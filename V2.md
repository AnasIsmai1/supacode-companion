# Supacode Companion v2 — Design

Status: design agreed, not implemented.
Date: 2026-08-22.

v1 is a remote keyboard for Claude sessions. v2 makes the phone a place to
close the loop: read what Claude changed, verify it, land it, recover when it
breaks — without walking to the Mac.

---

## 1. Understanding

- **What.** Read the diff, run the tests, commit/push/PR, recover — all from
  the phone, per worktree.
- **Why.** Today all four send you back to the Mac. The chat shows tool names
  and file paths, never content or outcome.
- **Who.** One operator, one Mac, phone on the tailnet.
- **How.** The companion executes git and shell in the worktree itself. It does
  not ask Claude to do it — that has to work while a session is busy, modal or
  wedged, which is exactly when you need it.
- **Boundary.** The tailnet. No auth. `/ws/raw` already grants arbitrary shell,
  so git-write is not a new class of exposure.
- **Non-goals.** Multi-machine, off-tailnet access, non-Supacode sessions,
  per-device identity, supervisor/auto-answer, screenshot capture.

## 2. Assumptions

1. One operator, one Mac, ~46 worktrees, ~33 zmx sessions. No concurrency design.
2. Reads target <200ms. Measured today: `/api/tree` 64ms, `/api/session` 134ms.
3. Command execution is free-form, not allowlisted. An allowlist would be
   theatre next to `/ws/raw`.
4. Reliability stays launchd `KeepAlive`. No queue, no durable retry.
5. Single maintainer. Fewest moving parts wins.
6. Git is scoped to worktrees `listWorktrees()` already knows. No arbitrary-path git.
7. The four v1 defects (§7) are fixed as part of v2, not deferred.

## 4. Prior art — omg.dev

[BennyKok/omg.dev](https://github.com/BennyKok/omg.dev), MIT. Architecturally
convergent and independently arrived at: Bun server, React/Vite PWA, tmux-owned
sessions, Tailscale for remote access, no auth by design. ~140k lines to our
5,426.

**Key difference.** omg.dev *spawns and owns* its sessions — its own worktrees,
its own sweeper, agents driven through SDK backends. supacode-companion
*attaches* to sessions Supacode launched. The mature parts of omg.dev's chat
depend on owning the process and are therefore not available to us. Its prompt
handling is the same tmux-pane scraping we do (`src/tmux.ts:1500-1600`).

**Borrowed:**

| Take | From | Cost |
|---|---|---|
| Structured diff | `src/session-diff.ts` (479 ln, MIT) | port, swap 1 fn |
| Diff rendering | `@pierre/diffs` npm 1.3.5 | 1 dep |
| Rating-overlay dismiss | `tmux.ts feedbackPromptOpen` | ~8 ln |
| Busy-meter primary signal | `tmux.ts BUSY_METER` | ~3 ln |
| Send serialize + type-confirm | `src/sendq.ts` ideas only, not the 687-ln queue | ~30 ln |

**Skipped:** `session-landing.ts` (hardcoded to their repo), SDK backends (need
to own the process), artifacts / scheduled agents / MCP subagents (different
product).

**Standing risk.** If Supacode is not load-bearing for you, this project is a
smaller reimplementation of a maintained MIT one. Decided: Supacode's tree is
the point, so we keep building. Revisit if that stops being true.

## 5. Design

### 5.1 Architecture

The new axis is the **worktree**. v1 routes key on a session (`/s/:sessionId`)
or surface (`/t/:surfaceId`); diff, git and runs all belong to the worktree,
which has no route.

- **Route:** `/w?wt=<worktree id>`. Query param, not path segment — worktree ids
  are already percent-encoded paths, so a path segment would need
  double-encoding. `App.tsx` already reads `location.search` for the terminal
  title.
- **Containment:** every route resolves `?wt=` against `listWorktrees()` and
  404s otherwise. The worktree list *is* the allowlist — already cached at 20s,
  already what decides what the phone can see. No second `safePath` resolver.
- **Entry points:** the `{branch} · dirty` subtitle at `Tree.tsx:47`, and a
  header button in `Chat.tsx` using the `session.worktreeId` it already receives.

### 5.2 Read path — `lib/diff.ts`

Port `omg.dev/src/session-diff.ts` near-verbatim, keeping its MIT header and a
provenance line.

Two changes:

1. `isSessionWorktree()` tests a `WORKTREE_ROOT` prefix; ours becomes a
   `listWorktrees()` lookup — i.e. the §5.1 containment rule, so it costs nothing.
2. It uses `Bun.spawnSync` throughout. `lib/sessions.ts:44` documents why that
   is wrong here (blocks Bun's event loop; polls queue behind it). Convert
   `git()` to the async `run()` shape `lib/worktrees.ts` uses, same 10s kill timer.

Endpoints mirror its three entry points:

| Endpoint | Function | Payload |
|---|---|---|
| `GET /api/diff/stat?wt=` | `computeSessionDiffStat` | counts only; cheap enough to fold into `/api/tree` |
| `GET /api/diff?wt=` | `computeSessionDiffSummary` | file list + per-file counts, no patch bodies |
| `GET /api/diff/file?wt=&path=` | `computeSessionFilePatch` | one raw patch, on expand |

**Semantic shift:** the diff is against the **fork point**
(`merge-base origin/main HEAD`), not the working tree — everything this session
changed on this branch, commits included. It deliberately does not `git fetch`
on this path; upstream's comment records that as the source of perceived
slowness.

### 5.3 Write path — `lib/git.ts`

Separate file from `lib/diff.ts` so the read path stays obviously read-only.
Same shape as `lib/supacode.ts`: private async `run()`, one export per
operation, 10s kill timer.

Five operations, deliberately not fifteen:

- `commit(wt, message)` — subject truncated to 50 chars (global rule); no
  Claude co-author trailer.
- `push(wt)` — adds `-u origin <branch>` when there is no upstream. Never force.
- `createPR(wt, title, body)` — shells to `gh` (2.97.0, confirmed installed).
- `restoreFile(wt, path)` — per-path only.
- `discardAll(wt)` — the only whole-tree destructive op; typed confirm on the phone.

### 5.4 Runs — `zmx run`, not Supacode

**The Supacode app is not required.** Verified 2026-08-22:

```
zmx run companion-probe-50486 -d bash -c 'echo HELLO; sleep 2; echo DONE'
→ session "companion-probe-50486" created
→ command sent!   exit=0
```

`zmx history --vt` on it then shows:

```
$ bash -c 'echo HELLO-FROM-RUN; sleep 2; echo DONE'; echo ZMX_TASK_COMPLETED:$?
HELLO-FROM-RUN
DONE
ZMX_TASK_COMPLETED:0
```

Consequences:

1. `zmx run <new-name> -d` **creates** the session. zmx is a binary at a known
   path, already wrapped by `lib/zmx.ts`. No app, no `supacode tab new`.
2. `ZMX_TASK_COMPLETED:<code>` is appended automatically — pass/fail from a
   regex on one line, no test-output parsing.
3. Existing machinery works unchanged: `/api/screen` renders it, `/ws/raw`
   streams it, `Screen.tsx` colours it. Still zero new process supervision.
4. zmx sessions outlive the companion. A restart or `KeepAlive` respawn does not
   kill a running build.

`POST /api/run?wt=` runs `zmx run companion-<worktree-hash> -d cd <wt> && <cmd>`.
One reusable runner session per worktree; zmx serialises per session, so a
second tap queues rather than interleaving.

Constraints from `zmx --help`, both acceptable: stdin is `/dev/null` (an
interactive prompt cannot hang you; genuinely interactive commands need
`zmx attach`), and commands are passed as-is, unquoted.

**The app is still needed** for `newWindow`, `closeWindow`, `newWorktree`,
`repo open` — v1 tree management only. `appRunning()` (finding 9) gates those
four buttons and shows "Supacode isn't running" instead of a 502. No
auto-launch: `supacode` has no headless mode and `supacode open` steals focus.

### 5.5 Send hardening

~50 lines across `lib/send.ts` and `lib/prompts.ts`.

1. **Type-confirm before Enter.** `sendText` writes text+Enter in one
   `zmx send`, then checks `stillInInput`. If the write delivered nothing, the
   box is empty, the check passes, and failure is reported as success. Split it:
   type → confirm text *appears* → Enter → confirm it *leaves*. Clear-and-retype
   on a failed type; the existing Enter retry ladder stays.
2. **Dismiss the rating overlay.** `1: Bad  2: Fine  3: Good  0: Dismiss`
   captures Enter and digits but renders as `N: label`, not the `❯ N. label`
   shape `parsePermission` matches. Detect and press `0` first.
3. **Serialize per zmx session.** Nothing stops two sends overlapping in one
   input box, and `sendText` holds the session ~1s across its retries. A
   per-session promise chain — no queue, no store.
4. **`queued` vs `sent`.** `lib/state.ts` already parses `queue-operation`.
   A send accepted mid-turn is in Claude's queue, not the transcript; show it
   as `queued`.

### 5.6 Busy signal

`lib/running.ts:34` keys on `/esc to interrupt/`. That footer rotates through
other hints mid-turn (`← for agents`, `PR #96`, tips), so busy state flickers.
Make the spinner meter shape primary — `(\d+m?\s?\d*s …tokens)` — with the hint
as fallback. ~3 lines; `SPINNER` already covers part of it.

### 5.7 Client

`/w?wt=` lazy-loads like `Chat`/`Terminal`/`Browse`. Header plus three sections:

- **Changes** — file list with `+/−` and status glyph; tap a file to expand into
  `<PatchDiff>` from `@pierre/diffs`. Summary endpoint means the list paints
  before any patch loads.
- **Run** — preset buttons from the worktree's `package.json` scripts, plus a
  free-text field. Result badge from `ZMX_TASK_COMPLETED`. Tap through to the
  existing Terminal view for full output.
- **Actions** — commit (50-char counter), push, PR, discard behind a typed confirm.

### 5.8 Service and ops

The daemon is healthy: launchd `state = running`, uptime 1d 22h at time of
writing, `companion.err` 0 bytes, 0 crashes. The 82 `runs` are dev kickstarts.

`tailscale serve --bg` **is** persistent — it writes tailscaled's `ServeConfig`;
no `tailscale serve` process exists. On this Mac the daemon is a system
extension (`io.tailscale.ipn.macsys.network-extension`) started at boot.

Real gaps:

1. No install script. The plist hardcodes the absolute repo path in four places.
2. The `web` build is outside the service — forget it and `public/` serves a
   stale bundle (README already lists this).
3. No single command that answers "is the whole chain up?"

`bin/sup` gains three verbs:

```
sup up        build web → generate+bootstrap plist → ensure serve config → status
sup status    launchd state · pid · uptime · port · HTTP · serve config · peer reachability · last err
sup restart   kickstart -k, then status
```

`sup status` prints peer reachability because "phone offline" and "server down"
are indistinguishable from the phone, and the former is what actually happened.

**Not building:** a hang detector. `KeepAlive: {SuccessfulExit: false}` catches
a crash but not a wedged event loop. Real hole; never once observed in 46h with
zero stderr. Add a `StartInterval` prober on the first actual hang.

## 6. Decision log

| # | Decision | Alternatives | Why |
|---|---|---|---|
| 1 | v2 deepens phone control | Harden v1; broaden reach; supervisor mode | The gap is doing work, not trusting or scaling what exists |
| 2 | Companion executes directly | Drive Claude via prompts; split read/write by risk | Must work when the session is busy or wedged; deterministic, free |
| 3 | No auth; tailnet is the perimeter | Shared secret; per-device tokens; write-gating | Raw shell already exposed; auth on git alone would be inconsistent |
| 4 | Fix v1 defects inside v2 | Ship v2 on top | One is a crash, one is a half-built feature |
| 5 | Split native vs terminal on data shape | All native; all terminal | Avoids a second process supervisor; keeps the diff readable |
| 6 | No screenshot capture | Headless browser pipeline | The phone has a browser on the same tailnet |
| 7 | Build diff first | All four together | Only capability with no workaround today |
| 8 | Runs use `zmx run -d` | `supacode tab new`; custom runner | Works with the app closed; exit codes free; survives companion restart |
| 9 | One runner session per worktree | Session per run | zmx serialises per session — queuing free, no cleanup sweep |
| 10 | No auto-launch of Supacode | `supacode open` on demand | No headless mode; steals focus. Degrade and label instead |
| 11 | `bin/sup up/status/restart` | Separate install script; Makefile | `bin/sup` already exists as the CLI fallback |
| 12 | `sup status` probes the whole chain incl. peer reachability | Trust launchd | Phone-offline and server-down look identical from the phone |
| 13 | Generate the plist, don't commit it | Keep the committed plist | Four hardcoded absolute paths |
| 14 | No hang detector | `StartInterval` prober | 46h uptime, 0 crashes. Revisit on first hang |
| 15 | Port omg.dev's diff, not its chat | Write our own; adopt omg.dev wholesale | Its chat depends on owning the process; its diff does not |

## 7. Build order

**Phase 0 — safety net.** This is what stops finding 1 recurring.
- `git init`, first commit
- root `package.json` + `tsconfig.json`, `bun run check` = tsc over `server.ts` + `lib/`
- fix the `startClaude` import (finding 1)
- declare the missing `Pending` fields (finding 10)

**Phase 1 — diff.** `lib/diff.ts` port, three endpoints, `/w?wt=` route,
Changes section, `@pierre/diffs`. The capability with no workaround today.

**Phase 2 — runs.** `POST /api/run`, `zmx run -d`, result badge, Run section.

**Phase 3 — git writes.** `lib/git.ts`, Actions section, `appRunning()` gating.

**Phase 4 — send hardening.** §5.5 and §5.6.

**Phase 5 — ops.** `sup up/status/restart`, generated plist.

**Phase 6 — independent leftovers.** `/share/:id` route + picker (finding 2);
wire `lib/events.ts` to replace 3s polling with hook push (finding 3).

## 8. Testing

Same style as today — assert-based, no framework, `bun <file>` self-checks.

- The unified-diff parser is pure: fixtures in `test.ts` covering rename
  notation, binary, untracked, truncation.
- Rating-overlay detector: one line of screen text.
- Type-confirm ladder: fixture screens for empty box / text present / text left.
- `git.ts` write ops: exercised against a throwaway repo in the scratch dir, not
  a real worktree.
